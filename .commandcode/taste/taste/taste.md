# Taste
- Prefers handing off implementation via a complete, self-contained spec document ("the entire project, not a summary") that lists every file with exact contents plus explicit agent instructions. Confidence: 0.9
- Wants agents to implement exactly as specified — create every file, run install/build, and fix only type or build errors; never redesign, restructure, rename, or "improve" the architecture. Confidence: 0.95
- Does not want extra libraries added beyond the decided stack (explicitly forbids helpers like Drei, Framer Motion, etc. for motion/3D work). Confidence: 0.9
- Prefers minimal, surgical fixes over rewrites when the build complains (e.g., inline eslint disables over rewriting a component; don't touch shaders unless GLSL fails to compile). Confidence: 0.8
- Treats accessibility and performance as non-negotiables in web builds: content before spectacle, works without WebGL, honors `prefers-reduced-motion`, native (non-hijacked) scrolling, keyboard and mobile parity, semantic HTML, visible focus, and explicit performance budgets. Confidence: 0.9
- Prefers a decided, opinionated modern stack for web projects (Next.js App Router + React + strict TypeScript, Tailwind, GSAP/Lenis for motion, Three.js/R3F with custom GLSL, Zustand) and expects it to be locked rather than debated during implementation. Confidence: 0.7
- Wants to visually verify the result in the browser on localhost, and expects the agent to start the dev server and leave it running for them to inspect; when the served page doesn't show the latest changes, the user's expectation is that the localhost instance itself be updated/restarted so the running site always matches the current code. Expects to be handed the running-site URL (e.g. http://localhost:3000) explicitly — asks "kasih saya linknya biar saya bisa buka" — so they can open it in their own browser rather than hunting for it. Confidence: 0.75
- Values distinctive, original design over generic/template-looking websites — reacts approvingly when a build reads as non-generic. Confidence: 0.6
- Prefers fully procedural visual content — custom shaders and in-browser generation over external 3D models, GLB exports, and asset pipelines (Blender, Draco, etc.) — explicitly to avoid asset-pipeline and licensing overhead. Confidence: 0.8
- Favours conceptually specific, thematically coherent imagery over abstract/generic decoration (chooses "a black hole" over "an abstract blob") and expects palette, microcopy, and motion choreography to reinforce one coherent theme. Confidence: 0.7
- Re-themes with legacy design tokens kept as aliases to the new values so existing utility classes and components keep working — prefers low-churn, backwards-compatible style changes over mass renames. Confidence: 0.6
- Treats project documentation (README, feature/risk docs, credits) as part of every change — patch specs include mandatory doc-update sections so docs never drift from the implementation. Confidence: 0.6
- Writes specs with a "where to tune" table (single knobs per visual property) and a "soft spots for the agent" section that pre-flags anticipated type errors and the exact one-line visual fixes to verify. Confidence: 0.6
- Reports bugs with minimal detail (e.g., just "there's an error") and expects the agent to reproduce and root-cause the issue itself — checking server logs, browser console, and runtime state — rather than being handed the error text. Confidence: 0.6
- Keeps creative content writing out of the agent's hands: user writes the hero, about, and case-study copy themself from fill-in-the-blank briefs ("rough answers, no polish"), and the agent is expected to implement provided content verbatim, using explicit placeholders (e.g. CHANGE_ME) rather than inventing personal details like profile URLs. Confidence: 0.8
- Treats "finishing" as a distinct phase from "building": once features are done, cuts remaining scope explicitly ("no CMS, no blog, no more effects/scenes") and wants launch hygiene, crash-proofing, and UX polish prioritized over any new functionality. Confidence: 0.8
- Wants defensive runtime robustness built into interactive features: error boundaries that fall back to a static poster, WebGL context-lost handling, quality-tiered DPR caps, and preloaders/intros that only play on first visit per session (repeat visitors and reduced-motion users are never re-gated). Confidence: 0.7
- Treats launch/SEO hygiene as required deliverable work: real OG image, favicon, JSON-LD structured data, analytics, permanent redirects for old URLs, real profile links, env/deploy checklists, and testing on real devices (phone + modest laptop). Confidence: 0.7
- Is pragmatic about performance tooling: sets concrete budgets (LCP < 2.5s, CLS < 0.1) but expects agents to ignore unavoidable warnings that stem from the chosen stack (e.g. Lighthouse's "unused JS" nag caused by Three.js). Confidence: 0.6
- Vets any proposed dependency against actual usage and added JS cost: refuses a library whose features would go entirely unused (e.g. Drei helpers against a custom-shader scene) or that duplicates an existing system (a second animation framework means two tickers, two easing vocabularies, and more bytes); adds helpers only the day real usage appears. Confidence: 0.7
- Judges UI from the perspective of real device use — a phone in hand or a physical mouse: text cursor preserved in form fields, tap targets at the 44 px guideline, no tap-highlight flash, no hover states stuck after a tap, a visible "you are here" active nav state (aria-current), and no canvas/scene element sitting behind copy on narrow viewports. Confidence: 0.75
- Practises explicit design restraint: deliberately rules out features that don't earn their place in the concept (no hamburger drawer when three links fit at 360 px, no extra scroll indicators when the hero scene already serves that role, no dark/light toggle that contradicts the theme, no text effects beyond word-level because fancier splits read as gimmicky). Confidence: 0.7
- Prefers one-line global config fixes over per-component patches when both solve the same problem (chose Tailwind's `future: { hoverOnlyWhenSupported: true }` over wrapping individual hover utilities). Confidence: 0.6
- Keeps the live localhost instance healthy while iterating: knows a production `npm run build` overwrites `.next` underneath a running dev server (causing stale/broken serving), so restarts the dev server from a clean `.next` and verifies the served HTML against the source before telling the user to hard-refresh. Confidence: 0.75
- Wants scroll to be the narrative driver on the homepage: motion is scrubbed to scroll — one continuous, keyframed camera path through named shots — rather than threshold-triggered tweens that play once and idle; treats the camera as the narrator (dollies, orbits, dives) with pinned beats where text holds while the world moves around it, and fixes framing problems at the architecture level (hole at the origin, camera travels) instead of patching positions. Confidence: 0.8
- Prefers conveying narrative through motion/choreography over explanatory prose — explicitly dropped a text "Manifesto" section from the page flow because a camera-driven flyover sequence does the job better (kept the file only as a possible return later). Confidence: 0.6
- Benchmarks the experience layer against top-tier interactive portfolio references (e.g. atlasmotion.com) and treats "at that level" as the bar; when the site feels flat by comparison, the honest diagnosis is structural (camera, choreography, shots), not polish — with the remaining gap attributed to real content/footage rather than code. Confidence: 0.6
- Judges procedural scenes by whether they read as painterly/filmic rather than "game-like" — deliberately uses fog density, film grain (Noise OVERLAY) and the warm palette to carry the painterly impression, and logs "reads game-like" as an explicit medium risk with those same knobs as the mitigations; rules out gimmicks that tip into game-feel (e.g. 3D text or a flag on the summit). Confidence: 0.8
- Layers environment state onto the same scroll-scrubbed timeline as the camera shots — time of day (dawn → morning → golden hour → night) is keyframed across the page so the atmosphere itself narrates alongside the camera instead of staying a static backdrop. Confidence: 0.6
- Believes what makes a scene feel expensive is dozens of small details each with its own timing ("puluhan detail kecil yang masing-masing punya waktunya sendiri") — scripts the scroll narrative as a time-of-day "moment map" where each phase reveals its own 2–3 details (dawn valley fog + birds, golden-hour cabin light, night snowfall + aurora + shooting stars + frost), so scrolling reads as watching a day pass rather than moving between sections. Confidence: 0.85
- Specifies per-detail resource tiers keyed to the existing quality levels (high/medium/low) — particle counts, shader layers, and entire effects disabled on low/fallback — and treats cheap-but-multiplicative cues (scroll-velocity-driven wind gusts, camera hover lean) as high-leverage detail. Confidence: 0.7
- Picks the pragmatic build option that keeps earlier work reusable and a documented upgrade path open (procedural scene now, with the SHOTS camera path reusable as keys for a future Blender image-sequence render) rather than one that discards the current architecture. Confidence: 0.6

- Treats smoothness of effect appearance as a hard requirement: atmosphere phase ramps use long smoothstep windows (aurora fades in across time 0.78→1.0, not a 0.1-wide cliff) and shader-uniform intensities are damped frame-independently (`u += (target - u) * (1 - Math.pow(0.05, delta))`, ~1s settle) so fast scrolling can never make snow/aurora "turn on" abruptly — the acceptance test is that effects creep in ("merayap masuk") rather than pop on ("menyala"). Confidence: 0.7

- Keys scroll-choreography shots off scroll geometry, never DOM/document order: a marker nested inside its parent section made document-order collection reverse the timeline (parent `contact` before child `approach`), snapping the scene backward and popping gated effects; the prescribed fix is sorting keys by computed scroll position. Confidence: 0.55

- Wants DOM chrome to follow the live scene continuously rather than stay locked to a fixed palette: one `accent` CSS variable is written every frame from the 3D atmosphere state (peach DUSK → ice-blue ICE across the night ramp) and hard-coded color classes (`text-violet`, `bg-cobalt`, `bg-dusk`) are swapped to that single token, so text, buttons, and progress bars recolor with the sky — "transisinya kontinu, bukan snap". Confidence: 0.65

- Judges text-over-scene legibility quantitatively (cites measured contrast ~1.6:1 as a failure) and expects readability fixes to come from composition and atmosphere, not typography: moodier/darker sky keys, thinner fog, moving the sun out of the text zone (behind the peak), shrinking the sun bloom, plus a permanent cinematic bottom/left scrim gradient and a `.on-scene` text-shadow utility — elements with solid backgrounds/borders are considered "safe" over scenes; secondary text tokens are chosen per background luminance (`muted` grey only on dark solid backgrounds, cream at 70–90% opacity + shadow over the bright scene). Confidence: 0.7

- Sets a hard ceiling on readability scrims/vignettes: darkening gradients over the scene are fine as a "standard film trick" only while they read as light falloff, not an overlay — explicitly caps the hero bottom-scrim alpha around 0.55→0.65 and warns that exceeding it "starts to feel like an overlay, not light". Confidence: 0.55

- Treats mount-order as the root cause class for broken interactive effects: creating GSAP `quickTo` animators before their DOM targets exist (element gated behind an `enabled` state that starts false) permanently freezes the animation, so the prescribed pattern is two effects — one that decides `enabled` (touch/reduced-motion checks) and a separate wire-up effect gated on `enabled` that adds listeners only after nodes mount — and the custom cursor stays hidden (opacity 0) until the first real mouse move so nothing sits parked at (0,0). Confidence: 0.6
